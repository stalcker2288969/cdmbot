# CDMBot

[![CI](https://github.com/stalcker2288969/cdmbot/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/stalcker2288969/cdmbot/actions/workflows/ci.yml)

Фреймворк для модульных тестов ассемблерных программ на **CdM-8 Mark 5** и **CdM-16**. На вход подаются программа и набор сценариев в YAML. CDMBot собирает программу один раз через Cocas и запускает каждый сценарий с отдельным состоянием процессора и памяти.

- [Руководство по CDMBot](docs/usage.md) — установка, сценарии, библиотеки, проверка проекта и отчёты.
- [Справочник YAML](docs/yaml-reference.md) — все поля набора сценариев и манифеста проекта с примерами.

## Быстрый старт

Распакуйте исходники CDMBot в любую папку. Установка работает для текущего пользователя и требует интернета для первой загрузки зависимостей.

- **Windows** — дважды нажмите `install.cmd`. Для запуска из PowerShell используйте `powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1`.
- **Linux и macOS** — в папке проекта выполните `sh ./install.sh`.

Установщик использует [uv](https://docs.astral.sh/uv/getting-started/installation/) для отдельного окружения и при необходимости загружает Python 3.12. Для CdM-16 он использует доступный JDK 17+ или загружает Temurin JDK 21 в пользовательский кэш. Первая загрузка JDK занимает около 200 МБ. После проверки обоих процессоров установщик добавляет команду в окружение пользователя. Откройте новый терминал и выполните:

```shell
cdmbot --help
cdmbot program.asm suite.yaml
```

Чтобы обновить CDMBot, запустите установщик из папки с новой версией. Команда `uv tool uninstall cdmbot` удаляет CDMBot из окружения uv.

### Установка вручную

Для установки через pip нужен Python 3.10 или новее. Для CdM-16 укажите JDK 17+ через `JAVA_HOME`, добавьте `java` и `javac` в `PATH` или установите `python -m pip install ".[managed-java]"`, чтобы CDMBot мог загрузить JDK при первом запуске CdM-16.

```shell
python -m pip install .
cdmbot examples/cdm8/add.asm examples/cdm8/add.yaml
cdmbot examples/cdm16/add.asm examples/cdm16/add.yaml
```

Можно также вызвать `python -m cdmbot`. Вместо исходника допускается готовый бинарный образ `.bin` с адреса 0.

## Набор тестов

```yaml
version: 1
architecture: cdm8
memory_model: unified
defaults:
  run: {max_steps: 100}
  setup:
    registers: {r2: 0x55, sp: 0xf0}
    memory: {0x80: [0x12, 0x34]}
  preserve_registers: [r2, sp]
  allowed_register_changes: [r0]
  preserve_memory: [{address: 0x80, length: 2}]
cases:
  simple:
    setup:
      registers: {r0: 10, r1: 32}
    expect:
      registers: {r0: 42}
  wrap:
    setup:
      registers: {r0: 255, r1: 1}
    expect:
      registers: {r0: 0}
      flags: {c: 1, z: 1}
```

| Поле | Назначение |
| --- | --- |
| `version` | Версия формата YAML. Обязательное значение — `1`. |
| `architecture` | `cdm8` или `cdm16`. Один набор использует одну архитектуру. |
| `memory_model` | `unified` по умолчанию. В режиме `harvard` образ загружается в ROM, а `setup.memory` и проверки работают с отдельной RAM. |
| `build.sources` | Список дополнительных файлов для Cocas. Пути считаются относительно YAML. Поддерживаются исходники, объектные файлы и библиотеки макросов. |
| `build.harness` | Тестовая обвязка. Позволяет передать саму библиотеку первым аргументом CDMBot. Обвязка задаёт точку входа, вызывает нужную подпрограмму или макрос и завершает программу. |
| `defaults`, `cases` | Общие настройки и обязательный словарь именованных сценариев. Настройки сценария имеют приоритет. Ключи регистров, флагов, памяти, `setup.input` и `run` объединяются. Списки, включая `setup.stack`, и `run.until` заменяются целиком. |
| `setup` | Начальные `registers`, `flags` и `memory`. Для отсутствующих регистров начальное значение равно нулю. |
| `setup.stack` | Значения на стеке перед первой инструкцией. Первый элемент лежит по адресу SP и первым читается через `pop`. |
| `setup.input` | Значения в RAM по меткам ассемблерной программы после линковки. Допустимы числа, текст и списки байтов. |
| `run.entry` | Стартовый адрес. По умолчанию CdM-8 начинает с 0, а CdM-16 выполняет штатный сброс по вектору в образе и затем применяет `setup.registers` и `setup.flags`. Явный адрес пропускает сброс CdM-16. |
| `run.until` | `halt` по умолчанию, `{pc: адрес}` до исполнения инструкции по этому адресу, либо `{steps: число}` после заданного числа инструкций. |
| `run.max_steps` | Бюджет инструкций от 1 до 10 000 000, по умолчанию 10 000. Исчерпание бюджета до условия остановки проваливает сценарий. |
| `expect` | Точные значения `registers`, `flags` и `memory` в момент остановки. Пустой сценарий проверяет достижение условия остановки. |
| `allowed_register_changes` | Список регистров общего назначения, чьи значения могут меняться между инструкциями. Пустой список запрещает такие изменения. Запись прежнего значения не наблюдается. Временное изменение с последующим восстановлением наблюдается. |
| `preserve_registers` | Список регистров, включая `sp`, которые должны иметь исходные значения в конце сценария. |
| `preserve_memory` | Список диапазонов `{address: начало, length: число_байтов}`, которые должны совпадать с начальным содержимым RAM при остановке. |

CdM-8 принимает `r0`–`r3` и значения до `0xff`. CdM-16 принимает `r0`–`r7` и значения до `0xffff`. Имя `fp` означает `r7` на CdM-16. `sp` доступен в `setup` и `expect`, `pc` — в `expect`. Адреса инструкций CdM-16 чётные. Флаги `c`, `v`, `z` и `n` записываются числами `0` или `1`.

Адреса памяти всегда байтовые. Запись `{0x80: 3}` описывает один байт, `{0x80: [0x34, 0x12]}` — два последовательных байта, соответствующих слову `0x1234` на CdM-16. В объединённой памяти `setup.memory` накладывается на загруженный образ, поэтому можно инициализировать область данных прямо в образе.

Шаг — одна инструкция. Сброс CdM-16 в счётчик не входит. При остановке по `halt` в отчёте виден PC после выборки инструкции. Остановка по адресу возможна до первого шага, как и `{steps: 0}`.

### Входные данные и стек

```yaml
setup:
  stack: [7, 3]
  input:
    start_label: 10
    text_label: "тест"
```

Каждый элемент стека и каждое число из `input` занимает один байт на CdM-8 или одно 16-битное слово на CdM-16. Слова записываются младшим байтом вперёд. Текст записывается в UTF-8, включая только указанные символы. Если программа ждёт завершающий ноль, добавьте его явно, например `"тест\0"`. Список `[0x41, 0x42, 0]` задаёт точные байты на обеих архитектурах.

Если указан `setup.registers.sp`, стек начинается по этому адресу. Иначе CDMBot размещает значения в верхних адресах RAM и выставляет SP на вершину. Для CdM-16 адрес вершины должен быть чётным. Программа может пользоваться подготовленным стеком сразу. Команда, которая меняет SP, меняет и адрес последующих `pop`.

В `input` можно ссылаться на уникальные локальные и экспортированные метки исходников, включая подключённые через `build.sources` секции, которые вошли в образ. Для готового `.bin` используйте числовые адреса в `setup.memory`. Резервируйте в ассемблере достаточно места под входные данные и стек. CDMBot проверяет границы RAM и пересечения между блоками `input`, `memory` и `stack`.

```shell
cdmbot examples/cdm8/inputs.asm examples/cdm8/inputs.yaml
```

## Запуск и отчёты

```shell
cdmbot program.asm suite.yaml --list
cdmbot program.asm suite.yaml --case "wrap*" --case "edge*"
cdmbot program.asm suite.yaml --jobs 4 --json --junit report.xml
```

Текстовый отчёт и JSON показывают, сколько сценариев найдено, выбрано и запущено, сколько прошло и сколько дало неверный результат. Отдельно считаются ошибки сборки, подготовки или запуска, выбранные сценарии без запуска и сценарии, исключённые фильтром. Одна ошибка сборки может оставить без запуска несколько сценариев. JSON также содержит конечное состояние процессора и расхождения по каждому сценарию. JUnit XML подходит для CI. `--case` принимает повторяемые шаблоны имён. `--jobs` задаёт до 32 параллельных сценариев, порядок результатов соответствует YAML.

| Код выхода | Значение |
| --- | --- |
| 0 | Все выбранные сценарии прошли или список сценариев выведен. |
| 1 | Хотя бы один сценарий завершился с расхождением или не достиг условия остановки. |
| 2 | Ошибка входных данных, сборки или окружения. Диагностика выводится в stderr. |

## Тесты библиотек

Передайте файл библиотеки как программу, а вызывающий код укажите в `build.harness`. В `build.sources` перечислите её зависимости. Это работает для подпрограмм в `.asm` и макросов в `.mlb`. Обвязка подпрограммы обычно объявляет экспортируемую метку через `ext`, вызывает её и выполняет `halt`.

```yaml
build:
  harness: harness.asm
  sources: [../lib/delta.asm]
```

```shell
cdmbot examples/project/lib/increment.asm examples/project/tests/increment.yaml
```

## Проверка проекта

```shell
cdmbot project examples/project/project.yaml --json --junit report.xml
```

```yaml
version: 1
source_roots: [lib]
suites:
  increment:
    program: lib/increment.asm
    suite: tests/increment.yaml
syntax:
  cdm8:
    architecture: cdm8
    directories: [lib]
    files: [tests/harness.asm]
structure:
  directories: [lib, tests]
  files: [tests/increment.yaml]
thresholds:
  file_percent: 66
  line_percent: 100
  comment_percent: 9
```

Пути в манифесте относительны к самому манифесту. `source_roots` рекурсивно собирает файлы `.asm` и `.mlb`. В `suites` перечисляются пары «программа или библиотека + YAML-сценарии». `syntax` компилирует группы исходников через Cocas. В каждой группе можно совместить `files` и `directories`. Запись `directories: [.]` проверяет дерево проекта, а `recursive: false` ограничивает поиск файлами непосредственно в указанных папках. `structure` проверяет наличие обязательных файлов и папок.

Отчёт показывает покрытие проекта, папок и файлов. Файл считается выполненным, если эмулятор прошёл хотя бы одну связанную с ним строку. Покрытие строк считается среди инструкций, сопоставленных с исходниками через отладочную карту Cocas. В отчёте видны строки, до которых исполнение не дошло, и файлы без карты. Для готовых `.bin` данные о строках отсутствуют. Макросы учитываются по месту, которое указал Cocas, обычно это строка вызова. Это покрытие исполнения строк, ветвления отдельно не измеряются.

Доля комментариев считается среди непустых строк. В неё входят отдельные комментарии и строки кода с комментарием. Отчёт также даёт отдельные счётчики пустых строк, строк кода и обоих видов комментариев. Символ `#` внутри строки или символьного литерала остаётся частью литерала.

Каждый ключ в `thresholds` задаёт независимый минимум от 0 до 100. CDMBot сравнивает покрытие с порогом до округления. Провал любого заданного порога, сценария или проверки синтаксиса и структуры даёт код `1`. Ошибка конфигурации, сборки набора или окружения даёт код `2`. Проверки остальных наборов продолжаются, если один набор не собрался.

## Расширение и разработка

YAML-парсер строит модель `Suite`. Ядро запускает сценарии и возвращает `CaseResult`, который используют CLI и форматы отчётов. Из Python можно загрузить `cdmbot.config.load_suite(Path("suite.yaml"))` и передать результат в `cdmbot.runner.run_suite(Path("program.asm"), suite)`. Параметр `backend=` принимает реализацию протокола `cdmbot.model.Backend`. При `jobs > 1` такой backend должен поддерживать параллельные вызовы `execute`.

CdM-8 исполняется на уровне инструкций по схеме Mark 5. В этой схеме `cmp` сбрасывает C, а `sub` выставляет C по переносу из старшего разряда. Внешние устройства, прерывания и специальные команды их обработки находятся за пределами модели. CdM-16 исполняется штатным Cocoemu из `cdm-devkit==0.2.3`, с моделями ROM/RAM без периферии. Справочник и исходники доступны в [cdm-devkit](https://github.com/cdm-processors/cdm-devkit).

```shell
python -m pip install -e .
python -m unittest discover -s tests -v
python -m pip install build
python -m build
```

GitHub Actions собирает пакет и прогоняет тесты на Windows и Ubuntu. Быстрый установщик проходит отдельную проверку на Windows, Ubuntu и macOS. Лицензия проекта — MIT.
