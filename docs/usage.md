# Руководство по CDMBot

CDMBot собирает программы через Cocas, запускает их в эмуляторе и сравнивает состояние процессора с правилами в YAML. CdM-8 Mark 5 использует встроенную модель инструкций, CdM-16 — Cocoemu. Оба режима моделируют процессор и память. Внешние устройства и подача аппаратных прерываний за пределами тестового окружения.

## Установка

Распакуйте архив с исходниками или установочный ZIP. Установка выполняется для текущего пользователя. При первом запуске установщик может скачать Python 3.12 и JDK 21, поэтому требуется интернет.

| Система | Команда |
| --- | --- |
| Windows | Двойной щелчок по `install.cmd`. |
| Linux и macOS | `sh ./install.sh` из распакованной папки. |

Установщик создаёт отдельное окружение через uv и запускает примеры на обеих архитектурах. Откройте новый терминал и проверьте команду `cdmbot --help`. Для обновления запустите установщик из новой копии проекта. Команда `uv tool uninstall cdmbot` удаляет установленный инструмент.

При ручной установке нужен Python 3.10 или новее. CdM-16 использует JDK 17+ через `JAVA_HOME` или `PATH`. Дополнение `managed-java` позволяет скачать JDK при первом прогоне CdM-16.

```sh
python -m pip install ".[managed-java]"
python -m cdmbot --help
```

## Первый тест

Запустите пример сложения для CdM-8 из корня проекта.

```sh
cdmbot examples/cdm8/add.asm examples/cdm8/add.yaml
```

Первый файл содержит программу, второй — архитектуру, набор начальных состояний и проверки результата. Для каждого набора CDMBot собирает один образ. Каждый сценарий начинает с отдельной копии состояния, поэтому запись в память в одном сценарии не влияет на остальные. После остановки CDMBot проверяет точные значения, сохранность памяти и регистров и выводит расхождения.

| Задача | Команда |
| --- | --- |
| Посмотреть имена сценариев без сборки | `cdmbot program.asm suite.yaml --list` |
| Запустить сценарии с заданным именем или шаблоном | `cdmbot program.asm suite.yaml --case "wrap*"` |
| Объединить несколько фильтров | `cdmbot program.asm suite.yaml --case simple --case "wrap*"` |
| Запустить до четырёх сценариев одновременно | `cdmbot program.asm suite.yaml --jobs 4` |
| Получить JSON и отдельный JUnit XML | `cdmbot program.asm suite.yaml --json --junit report.xml` |

`--jobs` принимает от 1 до 32. Порядок результатов соответствует порядку сценариев в YAML. Готовый `.bin` можно передать вместо исходника. Его первый байт загружается по адресу 0, а входные данные задаются числовыми адресами в `setup.memory`.

## Библиотеки и зависимости

Если тестируется подпрограмма, передайте файл библиотеки первым аргументом. В тестовом YAML укажите `build.harness` — вызывающий файл, который готовит запуск, обращается к экспортируемой метке через `ext` и завершает исполнение через `halt`. В `build.sources` перечислите дополнительные исходники, объектные файлы и библиотеки макросов. Обвязка также подходит для тестирования `.mlb`, когда она раскрывает нужные макросы.

```sh
cdmbot examples/project/lib/increment.asm examples/project/tests/increment.yaml
```

В этом примере `harness.asm` вызывает библиотеку `increment.asm`, а та обращается к `delta.asm`. Тесты передают аргументы в регистрах и проверяют результат и восстановление указателя стека. [Конфигурация тестов](../examples/project/tests/increment.yaml)

## Проверка проекта

Манифест `project.yaml` связывает тесты с программами и задаёт общие правила. Можно объединять наборы CdM-8 и CdM-16. Пути в манифесте считаются от его каталога. Пути `build.harness` и `build.sources` считаются от каталога YAML конкретного набора.

```sh
cdmbot project examples/project/project.yaml
cdmbot project examples/project/project.yaml --jobs 4 --json --junit report.xml
```

В режиме проекта CDMBot выполняет следующие проверки.

1. Проверяет обязательные файлы и каталоги из `structure`. Из `source_roots` рекурсивно собирает `.asm` и `.mlb` для отчёта о покрытии.
2. Компилирует группы `syntax`. В группе можно перечислить файлы, найти их в каталогах или совместить оба способа. Для проверки только корневых файлов используйте `directories: [.]` и `recursive: false`. Для проверки всего дерева укажите `directories: [.]` и оставьте рекурсивный режим.
3. Собирает и запускает наборы из `suites`. Ошибка сборки одного набора фиксируется в отчёте, после чего остальные наборы продолжаются.
4. Сводит покрытие проекта, каталогов и файлов. Для каждого указанного порога добавляет отдельную проверку в группу `coverage`.

Одна группа `syntax` использует одну архитектуру и общие библиотеки макросов. Если дерево содержит исходники для разных процессоров, заведите группы для соответствующих папок. `source_roots` задаёт область подсчёта покрытия, а `syntax` — область компиляции. Эти списки можно настраивать независимо.

## Покрытие и пороги

Покрытие файлов — доля исходников из `source_roots`, которым соответствует хотя бы одна исполненная строка. Покрытие строк — доля уникальных строк, исполненных среди строк инструкций, известных по карте Cocas. При нескольких наборах адреса сводятся по файлу и номеру строки. Для файлов, которые отсутствуют в карте, покрытие строк отображается как `n/a`. Отчёт измеряет достижение строк инструкций. Покрытие ветвей в эти показатели не входит.

Доля комментариев считается по исходникам и не зависит от запуска эмулятора. Учитываются строки только с комментарием и строки кода с комментарием. Пустые строки исключаются из знаменателя. Символ `#` внутри строкового или символьного литерала остаётся частью литерала. Метрика показывает количество строк с комментариями. Проверку смысла и качества комментариев следует проводить при ревью.

Включите только нужные условия в корневом блоке `thresholds`.

```yaml
thresholds:
  file_percent: 80
  line_percent: 75.5
  comment_percent: 20
```

Даже если все сценарии прошли, проект получает код `1` при провале любого заданного порога. Равенство порогу считается успехом. Значения в сводке округляются до двух знаков, а сравнение выполняется по исходному отношению счётчиков. Если метрика недоступна, соответствующий заданный порог проваливается. Удалите ключ, чтобы отключить конкретное условие.

В готовом примере выполнены 2 из 3 файлов и 8 из 8 строк с картой. При `file_percent: 67` проект провалится, хотя проверка строк при минимуме `100` пройдёт. Условие `comment_percent` проверяется отдельно. [Манифест с порогами](../examples/project/project.yaml)

## Отчёты и CI

| Поле статистики | Значение |
| --- | --- |
| `found` | Сценарии в загруженных YAML-наборах. |
| `selected` | Сценарии после применения `--case`. |
| `launched` | Сценарии, дошедшие до вызова эмулятора. |
| `passed` / `failed` | Успешные сценарии и сценарии с расхождением или неожиданной остановкой. |
| `errors` | Ошибки настройки наборов, подготовки сценариев или запуска окружения. |
| `not_run` | Выбранные сценарии, которые не дошли до эмулятора. Одна ошибка сборки может заблокировать весь набор. |
| `filtered` | Найденные сценарии, исключённые фильтром. |

JSON проекта содержит общую статистику, результаты наборов в `suites`, проверки в `checks` и покрытие в `coverage`. Для групп синтаксиса указывается фактический список `files`. В проверках покрытия доступны `minimum_percent`, `actual_percent` и причина провала. JUnit разбивает результаты на наборы сценариев и группы `syntax`, `structure` и `coverage`. Файл JSON можно сохранить перенаправлением стандартного вывода.

```sh
cdmbot project project.yaml --json --junit report.xml > report.json
```

| Код выхода | Значение |
| --- | --- |
| `0` | Все сценарии и проверки проекта прошли, либо команда вывела список сценариев. |
| `1` | Провалился сценарий, проверка синтаксиса или структуры либо порог покрытия. |
| `2` | Ошибка входных данных, сборки набора или окружения. |

При нескольких типах ошибок код `2` имеет приоритет. В CI используйте обычный код выхода команды для блокировки сборки и сохраняйте JUnit и JSON как отчёты.

## Если тест провалился

| Сообщение | Где проверить |
| --- | --- |
| `Cocas build failed` | Строку исходника из диагностики, архитектуру набора и список зависимостей. Для вызова из другого модуля проверьте экспорт и `ext`. |
| `label ... was not found` | Имя в `setup.input` и наличие секции с меткой в итоговом образе. |
| `Stop: expected ... got limit` | Условие завершения, точку входа и бюджет `run.max_steps`. |
| `overlaps ...` | Границы блоков `setup.memory`, `setup.input` и начального стека. |
| `Coverage ... is below the minimum` | Метрику в строке `FAIL coverage`, исходные счётчики в JSON и список файлов или строк вне покрытия. |
| `Coverage is unavailable` | Данные для выбранной метрики. Например, для `line_percent` нужен образ с картой исходников. |
